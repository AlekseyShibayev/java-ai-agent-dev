# Design

## Context

003 нормализует `permission.asked`/`permission.replied` в `PermissionAskedEvent`/`PermissionRepliedEvent` и умеет отвечать через `POST /api/chat/{sessionId}/permission/{requestId}`. 005 научил `chat.js` строить карточки инструментов из событий. Для разрешений не хватает представления, различимых имён событий и обработки устаревшего `requestId`.

Ограничения: офлайн, без JS-фреймворков, `build.gradle` не меняется, прод-код ≤ 300 строк, API 003 сохраняет форму.

## Goals / Non-Goals

**Goals:**
- Показать запрос разрешения с действием и ресурсами и дать ответить allow/reject.
- Не отправлять второй reply и не оставлять карточку в ожидании после ошибки.
- Проверить поведение в реальном браузере на фикстуре, без живой модели.

**Non-Goals:**
- Восстановление незакрытой карточки после перезагрузки страницы.
- Таймаут и авто-reject permission (002, вопрос 15).
- История прогонов, Markdown, сохранение правил из поля `save`.

## Decisions

- **Раздельные имена `permission.asked` и `permission.replied` вместо общего `permission`.** Клиент не угадывает смысл по наличию поля `reply`; это тот же приём, что `tool.*` и `usage.*` в 005. Единственный потребитель имён — `chat.js` в этом же репозитории.
- **Карточка строится в `chat.js`, а не шаблоном Thymeleaf.** Запрос появляется посреди прогона и живёт только до ответа; отдельный фрагмент и контроллер не нужны. Разметка повторяет подход карточек инструментов: DOM через `textContent`, данные модели не исполняются как HTML.
- **Ответ уходит `fetch`-ом в существующий `/api/chat/{sessionId}/permission/{requestId}`.** Это тот же путь, которым пользуется JSON API 003: нового endpoint нет, ответ 204 означает успех, JSON `{error}` — отказ. Сессия берётся из `data-session-id` блока ответа.
- **Повторный клик блокируется на карточке.** Кнопки получают `disabled` до завершения запроса, а признак ответа хранится на элементе: второй обработчик не отправит reply даже при двух быстрых кликах.
- **404 от OpenCode — это неизвестный запрос, а не недоступность сервиса.** `OpenCodeClient.replyPermission` превращает 404 в `NoSuchElementException`, `ChatErrorHandler` отдаёт 404 с текстом; 5xx и сеть остаются 502. UI по 404 показывает «запрос устарел» и гасит кнопки, по 502 — сообщение с возможностью повторить.
- **Чужую сессию отсекают и сервер, и клиент.** `SseBridge` не отправляет событие, чей `sessionId` не совпадает с сессией прогона; клиент дополнительно сверяет `data-session-id`. Серверная проверка авторитетна, клиентская сохраняет корректный DOM, если событие всё же попало в поток.
- **Закрытие карточки — удаление узла.** Успешный ответ и `permission.replied` убирают карточку; прогон при этом не завершается, composer остаётся в busy до `state`. Для устаревшего запроса карточка остаётся с текстом ошибки и без активных кнопок.
- **E2E на фикстуре с подменёнными `EventSource` и `fetch`.** Реальный Chromium загружает `chat.js`; сценарий подаёт события и задаёт ответ сервера вручную — без модели, секретов и сети.

## Risks / Trade-offs

- [Ответ уже дан в другой вкладке] → `permission.replied` закрывает карточку; запоздавший клик получает 404 и сообщение «запрос устарел».
- [Перезагрузка страницы теряет карточку] → осознанный non-goal: состояние прогона после reload восстанавливается, ожидающий permission — нет.
- [Разделение имени `permission` ломает внешних потребителей] → единственный потребитель — `chat.js`; контракт 003 не фиксировал имя, а 002 называл группу, не точный тип.
- [Удаление карточки скрывает, что ответ отправлен] → после allow прогон продолжается событиями инструмента, после reject приходит `state: interrupted`; пользователь видит актуальное состояние.
