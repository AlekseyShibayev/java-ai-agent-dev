# Design

## Context

004 даёт страницу `/chat` (Thymeleaf + HTMX + `chat.js` с нативным `EventSource`), 005/006 — карточки инструментов и разрешений, 024 — отдельный блок на каждый ответ. 007 дал Playwright-инфраструктуру: браузер ставится `playwrightInstall`, тесты идут тегом `e2e` в отдельной задаче `e2e`, по умолчанию headless, при падении сохраняются screenshot и trace в `build/playwright-artifacts`. Сценарии чата в 007 были отложены в 009.

Рантайм страницы: `POST /chat/messages` (HTMX) запускает прогон, `GET /chat/runs/{runId}/events` отдаёт SSE, `chat.js` дописывает текст по событию `text`. Рантайм получает события из общего потока OpenCode (`/api/event`), который читает `OpenCodeEventStream`.

## Goals / Non-Goals

**Goals:**
- Прогон страницы в настоящем Chromium против настоящего Spring Boot на случайном порту.
- Детерминированная проверка потокового ответа: вторая порция не отправляется, пока первая не отрисована.
- Ни одного обращения к OpenCode, Ollama и БД вне тестового профиля.

**Non-Goals:**
- Инструменты, разрешения, reasoning, usage (005/006/024 проверяются на своих уровнях).
- Повторная проверка инфраструктуры Playwright (007), кросс-браузерность, визуальные регрессии.
- Проверка самого OpenCode API: контракт зафиксирован фикстурами 000.

## Decisions

- **`@SpringBootTest(webEnvironment = RANDOM_PORT)` + `@ActiveProfiles("test")`.** Это единственный способ проверить HTMX-обмен и SSE так, как их видит браузер; `MockMvc` SSE не воспроизводит, а фикстура из 007 обходит серверную часть.
- **Стаб — подкласс клиента OpenCode с `@Primary`, а не HTTP-заглушка.** HTTP-заглушка потребовала бы эмулировать ещё и SSE-формат и Basic auth, то есть проверять транспорт вместо страницы; подмена бина оставляет реальными контроллеры, реестр прогонов, парсер событий и `SseBridge`.
- **Стаб отдаёт события кадрами SSE и блокирующим потоком.** Так работает реальный `OpenCodeEventStream` → `OpenCodeEventParser` → `RunRegistry` → `SseBridge`, и E2E не обходит конвейер событий.
- **Сценарий сам управляет порциями ответа (актёр), а не спит фиксированные паузы.** Тест отправляет первую порцию, ждёт её в DOM и только потом отправляет вторую; медленная машина не делает «ответ одним куском» ложноположительным, а быстрая — ложноотрицательным.
- **Сессия OpenCode — новая на каждый тест.** Каждый тест открывает свой браузерный контекст, поэтому у него своя HTTP-сессия и свой `sessionID`; события одного теста не попадают в прогон другого.
- **`build.gradle` не меняется.** Задачи `test` (исключает `e2e`) и `e2e` (включает `e2e`, ставит Chromium) уже есть.

## Risks / Trade-offs

- [`@SpringBootTest` поднимает H2 и Liquibase] → медленный старт на класс, но профиль `test` уже проверен контекстным тестом; альтернатива с отдельным профилем без БД потребовала бы правки конфигурации ради теста.
- [Подмена бина скрывает поломку реального HTTP-клиента] → контракт клиента покрыт тестами `opencode/*` и фикстурами 000; E2E отвечает за страницу.
- [Блокирующий поток стаба живёт до конца контекста] → поток виртуальный и демонический, JVM не держит; контекст закрывается вместе с классом тестов.
- [Браузерные тесты не идут в `./gradlew test`] → `e2e` запускается отдельно и в CI пока не стоит; это осознанно: приёмка требует зелёного `test` и отдельного `e2e`.

## Migration Plan

Только новые тестовые файлы и change; production-код не меняется. Откат — удалить тесты, change и строку задачи.
