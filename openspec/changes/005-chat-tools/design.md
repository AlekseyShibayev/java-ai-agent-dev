# Design

## Context

004 даёт страницу `/chat` с текстом ассистента и состоянием прогона. 003 уже нормализует события в `RunEvent` и публикует их в браузер через `/chat/runs/{runId}/events`. `OpenCodeEventStream` после `session.step.ended` читает `/api/session/{id}/message` и публикует `ToolResultEvent` из части `tool` — то есть результат уже приходит из сообщения, а не из события. Не хватает представления: `chat.js` обрабатывает только `text` и `state`.

Ограничения: офлайн, без CDN и JS-фреймворков, `build.gradle` не меняется, прод-код ≤ 300 строк, API 003 и серверный рантайм не трогаются.

## Goals / Non-Goals

**Goals:**
- Показать шаги прогона в том же потоке, что и текст: инструменты, reasoning, стоимость.
- Не исполнять разметку модели и не терять уже показанное при переподключении.
- Проверить поведение в реальном браузере на фикстуре, без живой модели.

**Non-Goals:**
- permissions (006), история прогонов между перезагрузками, Markdown и подсветка кода.
- Изменение формата API 003 и серверного рантайма.

**Decisions**

- **Разные имена SSE-событий вместо `kind` в JSON.** `RunEventNames` отдаёт `tool.started`, `tool.called`, `tool.result`, `tool.failed`, `usage.step`, `usage.session`; `reasoning` остаётся одним именем. Клиент подписывается на конкретный тип и не угадывает форму по полям. Альтернатива с полем `kind` меняет тело DTO и требует правок всех записей.
- **Карточка создаётся на `tool.started`, дополняется на `tool.called`.** Имя инструмента есть только в `session.tool.input.started`, вход — в `session.tool.called`; карточка живёт по `callId`, поэтому события могут прийти в любом порядке.
- **Результат сопоставляется по `callId` с вызовами текущего прогона.** `OpenCodeEventStream` публикует результаты всех сообщений сессии, включая прошлые ходы; клиент игнорирует `tool.result` для неизвестного `callId`, чтобы не показывать чужие карточки. Дедупликация повторного результата — по тому же `callId`.
- **DOM собирается через `textContent`, а не `innerHTML`.** Вход инструмента и результат — данные модели; экранирование на клиенте обязательно. Текст ответа по-прежнему приходит с сервера уже экранированным.
- **Reasoning — `<details>`, закрытый по умолчанию; дельты дописываются в конец `<pre>`.** Никакой перерисовки блока: тот же текстовый узел растёт, что видно в E2E по сохранённой ссылке на элемент.
- **Стоимость прогона — сумма `usage.step.cost`.** `usage.session.cost` кумулятивен по всей сессии и для прогона неверен. Токены — сумма `usage.step.tokens`. Формат — `$` + шесть знаков после точки, чтобы `0.000058` не превращалось в `0.00`.
- **Ошибка при остановке не рисуется.** События `tool.failed` с типом `aborted` игнорируются, а после `state: interrupted` новые ошибки не создают карточек. Прогон не помечается проваленным: статус меняют только `execution.*`.
- **E2E на фикстуре с подменённым `EventSource`.** Реальный браузер загружает `chat.js` и разметку, сценарий подаёт события вручную — без модели, секретов и сети. Серверные проверки (имена событий, крючки разметки) остаются в `./gradlew test`.

## Risks / Trade-offs

- [Клиентская фильтрация чужих результатов] → в буфер прогона всё равно попадают результаты прошлых ходов; при переполнении буфера прогон закрывается ошибкой (поведение 003). Фильтр не даёт им стать карточками.
- [Сумма шагов может разойтись с итоговой стоимостью сессии] → для отображения выбирается сумма прогона; расхождение с `usage.session` допустимо и не показывается.
- [Переименование событий ломает внешних потребителей `/api/chat`] → единственный потребитель — `chat.js` в этом же репозитории; контракт 003 не фиксирует имена `tool`/`usage`.
- [Много DOM-узлов при длинном reasoning] → дельты дописываются текстом, без повторного парсинга HTML; блок свёрнут и не влияет на вёрстку.

## Migration Plan

Меняются имена событий браузерного потока и добавляются обработчики. Откат — вернуть прежние имена и удалить обработчики; API и данные не затрагиваются.
